## 已实现边界

- 随机邀请只持久化 SHA-256 摘要及有效期；24 小时是本地工程邀请过期值，未作为正式 D08 冻结结果。重新准备邀请作废旧邀请；申请、审批都复验到期及消耗状态。
- 匿名邀请仅显示发起人账号尾号、三步参与说明、三种用途、向本项目发起人共享的范围及拒绝/撤回权利，不显示私人书名、姓名、故事或素材。当前身份模型没有账号姓名；尾号只能供双方核对邀请来源，不能证明真实身份，真实展示文案和核验仍待 D08。
- 申请记录告知版本和本人操作证据，不授予内容权限。发起人确认按 project → subject 顺序锁定，一次只绑定一位申请人，不能把付款账号绑定为另一讲述者。确认成功、绑定历史和 T10 首次参与事实同事务写入；事件 ID 和时间由服务端生成，重放、重新登录和换绑不重置起算时间。
- 采集保存、AI 处理、向发起人共享各自留存 subject、操作人、用途、接受/拒绝、告知版本、方式、证据及绑定/访问版本。AI 有单独许可且仍以采集许可为前提。拒绝不取消订单、首本权益或客服入口。
- 项目内容查询每次从当前 subject、绑定版本、用途及 access_epoch 计算访问；写命令校验 expectedBindingVersion / expectedAccessEpoch。授权变化和撤回递增 epoch；旧命令重放再次核对当前身份、版本和 epoch，不缓存可绕过鉴权的敏感结果。当前内容仅为已实现的项目元数据；录音、AI 任务、素材和故事消费者仍由后续责任票接入。
- 客服仅增加账号换绑所需共享工单记录、查询和表单。用户申请目标账号不授予其权限；客服须有 `care:write`、有效 MFA 管理会话、CSRF、存在且匹配项目/目标/来源版本的工单、合成 D08 告知与证据。换绑原子更新 bound_user_id、绑定版本、access_epoch 和工单，追加不可变绑定历史并与成功审计同事务提交。相同意图重放不再次迁移；异载荷冲突，旧绑定账号立即失去本项目访问，新账号不继承旧同意，其他项目身份不被全局撤销。
- 小程序 order → invite、welcome 和首页“我的参与与授权”接入 live 请求，支持当前账号的申请/参与恢复；不读取 demo 项目或使用 demo 总授权开关。邀请通过原生分享回调返回真实令牌路径，申请后等待审批；本人在同页分别选择、拒绝或撤回用途，并可提交换绑工单。管理端增加共享工单列表、详情和必要换绑表单。没有实现 T12 同机协助、T13 计划编辑或 T24 跨任务/生产联动。

## 公开接口

用户接口前缀 `/v1`：

| 接口                                                       | 边界                                                           |
| ---------------------------------------------------------- | -------------------------------------------------------------- |
| `GET /invitations/:token`                                  | 匿名最少参与信息，无私人内容                                   |
| `POST /projects/:id/invitations`                           | 已付款项目发起人准备/替换邀请                                  |
| `POST /invitations/:token/requests`                        | 登录本人申请，记录参与告知                                     |
| `GET /participations`                                      | 当前账号已绑定项目或仍有效的待确认申请，无私人标题             |
| `GET /projects/:id/binding-requests`                       | 发起人查询待核对申请                                           |
| `POST /binding-requests/:id/approve`                       | 发起人确认、并发绑定与一次参与事实                             |
| `GET /projects/:id/participation`                          | 当前合法两角色查询用途、动作与版本，拒绝后仍可进入客服         |
| `GET /projects/:id`                                        | 当前本人采集许可，或本人采集及对发起人共享许可后读取项目元数据 |
| `POST /projects/:id/consents`                              | 本人逐用途同意/拒绝，验证绑定版本和 epoch                      |
| `POST /projects/:id/consents/revoke`                       | 本人基础撤回，立即递增 epoch                                   |
| `GET/POST /projects/:id/care-requests`                     | 当前合法两角色提交或查询换绑申请；写入按幂等键去重             |
| `GET /admin/care-requests`、`GET /admin/care-requests/:id` | 有权客服查询最小工单及绑定历史                                 |
| `POST /admin/projects/:id/rebind`                          | MFA/权限/CSRF/工单/本人证据/来源版本全部校验后执行原子换绑     |

新迁移 `202610230011_invitation_consent` 增加邀请、申请、分用途同意、幂等命令、最小客服工单及绑定历史；已有迁移未修改。T10 `ProjectServiceTerms.read` 仅新增可选事务参数，在持项目锁的组合调用中复用连接。

### 原 Spec P2 第二次修复：200 应答跨本地会话到期

Spec 复审固定 `6c723d3545a393ba2e7a5bb31c5202bd4ce0083a`，确认上述会话恢复 P2 尚未完全闭合：请求发出时本地会话有效，服务端 200 返回前本地 TTL 到期，实际 SessionClient 会抛 `STALE_RESPONSE`（status 0），原来只处理 401 的恢复仍会丢弃 busy 结束与登录提示。本次为同一 P2 的第二次修复，不认定前一提交已完整解决，也不能用前一提交的 CI 或审查结论合并。

welcome / invite 的局部恢复仅增加 `STALE_RESPONSE` 且 status 0 的分支；原有当前页面代次、live 模式、原 context 非空及当前 context 为空的守卫保留。收到这类失效结果时清理旧状态、解除 busy、显示“登录已失效，请重新登录”；当前有效新账号及离页迟到结果继续丢弃。没有增加通用时间机制，没有改变 SessionClient、WXML、API 或迁移。

`13-spec-session-ttl-red.log` 通过实际页面 bundle 和实际 SessionClient 复现七条路径（welcome 刷新/申请/用途提交/换绑申请，invite 刷新/准备邀请/审批）全部 busy 未结束；请求前设有效期1秒，应答前可控 Date 直接推进2秒，无自然 sleep。`13-spec-session-ttl-green.log` 17/17；各路径都在 200 跨 TTL 后恢复未登录状态，并通过实际 wx.login/request 边界再次登录。新增的新账号和离页成功迟到回归也通过，连同既有相关页面/会话/订单回归为 `13-spec-session-ttl-regression.log` 41/41；最终参与页面文件19/19。`pnpm run typecheck:frontend` 和 `pnpm run build:frontend` 通过，构建日志为 `13-spec-session-ttl-build.log`，`git diff --check` 通过。本次没有 WXML/后端变化，未重复浏览器、原生或数据库套件；新固定提交仍须双轴复审与最终 CI 成功。
