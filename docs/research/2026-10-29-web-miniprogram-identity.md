# 网页与小程序共用账号：身份调研

日期：2026-10-29。代码核对基线：`afe149c10c3b66e5fe6b051581c42c5011929f04`，结合工作区当前的 CONTEXT/GLOSSARY/ADR；未修改业务代码，未检查秘密值，未登录微信管理后台，未注册应用或调用付费服务。

本报告区分代码事实、微信官方文档事实与建议。用户已确定网页使用 `sgl.wootoon.cn`，并要求与小程序互通；后续明确首版用于完成内部验收，账号可以简化。当前实施方向为预建内测账号与短期一次性登录链接，不先接短信或邮箱供应商。本报告不是已实施或真实平台验收记录。

## 结论

互通应定义为：同一个人通过不同登录方式进入同一个 TimeNook `User`，看到其获授权的同一批项目、故事与订单；网页和小程序各有独立会话。现有数据库已经将内部用户 UUID 与微信身份分开，适合扩展，无需为网页复制项目。

但目前登录和部分业务检查仍依赖小程序微信身份，不能仅增加一个网页登录按钮就宣称互通完成。按用户最新的内部验收范围，可先创建独立于微信的内测 User，通过受控发放的短期一次性链接登录；等微信配置就绪后，通过用户主动证明两种身份的控制权，将真实微信身份绑定到同一个内部 User。AppID 为空期间只能验证关联协议与权限的隔离测试，不能记录为真实微信互通通过。

## 微信官方文档事实

本轮官方页面在网页抓取工具中返回不可读取；通过 Context7 检索到的微信官方文档内容核实，下列链接均指向原始拥有者。未使用社区转载作为结论依据；平台实际权限、应用是否获批及后台配置尚未核验。

| 机制 | 已核实的边界 | 来源 |
| --- | --- | --- |
| 小程序 UnionID | 小程序绑定微信开放平台后，可通过 `wx.login` 与服务端 `code2Session` 获取 UnionID；不能假定未绑定时必有此值 | [UnionID 机制](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/union-id)、[code2Session](https://developers.weixin.qq.com/miniprogram/dev/server/API/user-login/api_code2session) |
| 微信内网页授权 | 当前官方服务号文档要求使用已认证服务号的 AppID，并登记网页授权回调域名；授权入口与小程序 code 兑换不同 | [微信网页授权](https://developers.weixin.qq.com/doc/service/guide/h5/auth) |
| 网页授权 scope | `snsapi_base` 主要取得该服务号下 OpenID；`snsapi_userinfo` 取得用户同意后提供相应用户信息，不应为取得资料默认索取无关信息 | [网页授权说明](https://developers.weixin.qq.com/doc/service/guide/h5/auth) |
| 服务号 UnionID | 官方用户信息接口指出，服务号关联开放平台后才有相应 UnionID 字段；仅有网页登录成功不保证跨应用身份可统一 | [获取授权用户信息](https://developers.weixin.qq.com/doc/service/api/webdev/access/api_snsuserinfo.html) |
| 网站应用微信登录 | 需要开放平台已审核的网站应用及其 AppID/Secret；`qrconnect` 使用 `snsapi_login`，面向 PC 的二维码授权流程不是服务号网页 OAuth | [网站应用微信登录](https://developers.weixin.qq.com/doc/oplatform/Website_App/WeChat_Login/Wechat_Login.html) |
| 网站登录身份 | 服务端用授权 code 兑换该网站应用的授权信息，文档提供 OpenID 与 UnionID；需要保留所属应用和开放平台范围 | [网站应用 UnionID 接口](https://developers.weixin.qq.com/doc/oplatform/Website_App/WeChat_Login/Authorized_Interface_Calling_UnionID.html) |

由此推导：小程序、服务号和网站应用不是同一个 AppID；域名相同也不会自动让其 OpenID 相等。希望通过微信自动识别同一个人，必须配置相应应用并在同一开放平台身份范围内使用服务器验证的 UnionID。若某次响应缺少 UnionID，应保留已有明确绑定或走主动关联，不能猜测身份。

## 当前首版方案：预建内测账号与一次性登录链接

这符合用户“首版完成内部验收、账号可以简化”的最新范围，不依赖短信、邮箱或可用小程序 AppID。

1. 通过受控 CLI 创建内测 User；当前 users 表允许没有任何 `WechatIdentity`，会话外键只要求 User 存在。[用户与会话迁移](../../apps/api/prisma/migrations/202610220003_identity_sessions/migration.sql)
2. CLI 为指定内测 User 签发高熵随机短期票据，数据库只保存摘要、User、用途、到期与消费状态。票据在私有输出中交给操作员，不提交 Git、不写访问日志；不提供公网“列出账号”或“输入 User ID 领取登录链接”的接口。
3. 浏览器显式完成兑换后签发正常网页会话。票据原子单次消费，过期、无效、已使用统一失败；避免浏览器预取/链接扫描直接消费登录票据。成功后从地址栏清除票据，页面使用 no-referrer/no-store。
4. 网页使用同一个内部 User 和现有服务端授权检查。发起人、讲述者、无关用户至少三个独立身份；内测账号也不能任意选角或绕过本人同意。
5. 先把“预建账号可登录”和“预建项目可操作”分成两个公开行为验证。后者受现有订单外键、商业参数和参与模块测试配置限制；需要明确的内测数据装配，不能将测试付款记录成真实付款。若复用现有合成 fixture，应隔离数据库/对象空间、固定内测标识，并禁止真实收款和生产操作。

以上票据和会话防护为工程建议，并非已实现结果。具体有效期与受控发放方法由实施规格固定，不把内部登录链接做成永久凭证。

## 将来正式网页登录的候选方案

以下仅为后续正式产品的比较，不纳入当前内测首版，也不再要求现在选择短信/邮箱方案。

| 方案 | 用户体验 | 当前前提与代价 | 建议 |
| --- | --- | --- | --- |
| A：手机号验证码为网页主入口，小程序首次主动关联 | 手机浏览器输入手机号和验证码；小程序就绪后，用户在自己的会话中验证同一手机号并明确关联；两端返回同一个内部 User | 不依赖小程序 AppID 启动网页，但需短信服务、签名/模板及真实发送验收；当前仓库未接入。手机号是登录凭据，不应等同讲述者本人身份 | 面向国内手机用户的后续候选；首版不实施 |
| B：微信优先 | 微信内网页走服务号 OAuth，桌面可走网站应用扫码；同一开放平台范围的 UnionID 关联至同一内部 User | 依赖已认证服务号/网站应用审核及绑定；手机外部浏览器的具体体验需另外确定；无法仅靠小程序申请完成解决所有渠道 | 若现有可用服务号与开放平台应用齐全，体验连贯；否则会继续受平台条件阻塞 |
| C：邮箱验证码或一次性登录链接 | 浏览器直接验证邮箱，小程序后续显式关联；不依赖微信网页能力 | 需要发信域名和邮件供应商、投递验收；切换邮箱应用对部分年长讲述者不方便 | 适合作为内部验收或确有邮箱使用习惯的目标用户入口，不默认替代国内手机用户登录 |

受控内测身份可以验证账号与权限协议，但不能放成公网任意选择身份的入口。若后续选择 A/C，不能因短信/邮件尚未配置就让生产接口返回验证码或固定验证码。

## 共用账号与关联规则建议

1. 以 `User.id` 作为资料归属的稳定标识；认证身份只负责证明进入哪个 User。网页登录不产生第二套人生项目，不重新发放首本权益。
2. 微信身份键保留 AppID/OpenID；新增手机号/邮箱身份时，记录经过服务端验证的规范化标识。UnionID 应连同已配置的开放平台范围存储，不能跨不同范围裸比字符串。
3. 对已登录用户新增登录方式，要求新方式的独立验证与明确关联操作；将短期挑战绑定当前会话、目标身份及操作，单次消费，限次数和有效期。当前最小方向：已登录网页发起关联，小程序端用新的 `wx.login` code 由服务器兑换真实微信身份，双端明确确认，再事务写入关联。关联票据与正式登录会话分开，不能凭网页端自报 OpenID 绑定。
4. 未绑定过的新微信身份可在证明两边控制权后关联已有网页 User；如果两边已各自拥有不同 User，第一版返回明确冲突并进入受控处理，不自动搬运订单、故事、授权和财务事实。小程序首次走“关联现有账号”时应在创建新 User 之前完成查找和确认，避免先自动开户再被迫合并；并发请求依赖数据库唯一约束和身份事务锁，而不是先查后写的应用判断。
5. 不按昵称、头像、自报手机号、仅有邀请链接或相似资料认定同一人。手机号回收/换号场景需要保留撤销与重新验证路径；尤其不能把手机号登录等同本人采集/AI/入书同意。
6. 网页与小程序分别签发会话，共用同一账户与授权检查。网页建议使用同源受保护 Cookie、CSRF 与服务端会话；小程序可保留 Bearer。跨端互通不要求在 URL、localStorage 或二维码里传递正式会话令牌。
7. `sgl.wootoon.cn` 的落地页和网页产品可分别占 `/` 与 `/app/`；用户 API 由同源入口转发到同一个 TimeNook API。浏览器路径不构成不同安全域，需一并检查落地页脚本、缓存与 Cookie 作用域。管理端继续使用既定独立入口和权限。
8. 第一个实现切片至少验证：网页首次注册、小程序关联、重复/并发关联、已被占用身份、缺少 UnionID、退出与撤销、两端同项目读取、外人拒绝，以及发起人不能通过关联变成讲述者。

## 当前已收敛与剩余条件

已收敛：首版内部验收，简化账号；采用预建内测 User 和短期一次性登录链接，不先接短信/邮件，保留小程序显式关联同一 User 的协议与工程验证。

“网页登录需要和小程序互通”已明确资料和权限共用，不必重复询问是否愿意共用数据。当前待实施规格落实的是：内测票据受控发放、项目/测试订单装配与隔离、跨端关联状态及冲突处理。真实小程序 AppID/Secret 和平台登录仍为外部条件，不能用合成结果追认通过。
