## 行为与持久约束

买方申请与共享客服工单绑定；客服核验原销售 D07 的固定金额和权益后果，不接受临时金额。订单锁 → 项目锁下预留资金，成功与未知/处理中/异常预留之和不超过实收，批准立即冻结新的投产。申请、商户退款号及已批准金额/政策/负责人/期限不可变，重复命令不延长承诺。

退款请求先保存稳定单号，再调用微信；超时或验签不通过保留原预留，并先查询原退款。通知验签/解密、核对订单/交易号/金额/商户后先持久化 Inbox，再与查询共用入账。退款异常不释放预留；明确关闭才释放，已核实成功不会被迟到异常覆盖。后台补扫未处理 Inbox 和长期未终态原退款。

原交接未知时必须先在 T23 核对实际接单或取消，再记录同尝试的核验证据；退款工单不能直接写实物成功状态。退款不删除资料、付款或生产历史。全额终止与部分保留按原快照区分；质量救济保留原单处理语义。退款时仍在实际制作的权益保持已消费；之后核实取消，按已冻结的取消后果撤销，不恢复另一份首本。

## 独立审查修复

固定候选 `02c1cab` 的独立 Standards 与 Spec 都复现了同一 P1：提交权限预检事务结束后，另一客服可先驳回该批准并释放资金，再批准替代退款；旧实现最终提交未重验当前状态，仍把已驳回申请变为 unknown 并外呼，导致预留超过实收。Spec 另发现 P2：用审批当日判断申请窗口，会错误拒绝及时申请、跨期核验的请求。

P1 在真实公开 HTTP 中复现：仅使用测试构造的调度暂停控制，`/submit` 预检后由另一实际 MFA 客服 `/reject` 并批准另一笔，再恢复原请求。RED `/tmp/timenook-t27-review-red-execution-fence.log`：旧实现201并执行退款；GREEN `/tmp/timenook-t27-review-green-execution-fence.log`：当前请求409、原单仍 rejected、零新增供应商提交、预留保持99900。没有 mock 退款业务或新增测试用产品 HTTP。

真正首次提交、查询明确不存在后的重试以及入账，都在订单锁内重验有效预留状态、原批准金额及实收资金总额；已结束申请不能借另一笔的资金执行。活动预留状态使用同一常量与判断，列表、驳回、入账及执行不再各维护一份枚举。另验证原退款不存在的查询飞行期间收到已验签 CLOSED、再批准替代退款时，不发生旧号再提交或超额预留。

P2 RED `/tmp/timenook-t27-review-red-request-window.log`：及时申请跨期核验409。修复后按不可变原申请时间与原政策资格窗口核验；保存原窗口起止、申请时间、独立核验时间和处理截止时间。资格窗口前/恰好/后、及时申请跨窗口仍可审批/执行、处理截止前/恰好/后及重放不延长均经公开 HTTP 验证。补充的事实字段通过增量迁移保护，原迁移未改写，旧批准不回填虚构窗口证据。
