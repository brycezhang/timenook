# MVP 工程复杂度复核

日期：2026-10-22。依据当前规格、30 张 tickets、已合并工程和受控探针文档。本文保留当时审视依据；用户随后确认按结论简化。当前执行规则见[实施规格](spec.md)与[ADR 0010](../../adr/0010-mvp-fixed-policy-and-reuse.md)，本轮已同步 30 票，未删减 MVP 功能、调整依赖或修改业务代码。

## 判断

存在可压缩的工程复杂度，主要在首版政策的配置空间、探针到生产的重复建设风险、运营功能的自动化程度，以及规格的重复表达。模块化单体、私有存储、可靠任务和确定版本交付本身有明确的首单价值，不能仅凭组件多就判定过度设计。

本次 to-spec 补漏解决的是既定要求无人负责或互相矛盾的问题。补上期限、换绑、文件标识的验收归属，并不要求把这些能力做成通用规则引擎或完整运营平台。

## 从结果倒推最小系统

首版承诺是一位成年讲述者与一位发起人，用 999 元完成一个项目和一本实体书。首批 30–50 个项目首先需要回答：用户是否愿意讲、能否完成、成书是否满意、人工与供应商成本能否承受。系统需要交付五个结果：

1. 钱款对应唯一项目与首本权益，退出或重试后可继续。
2. 有效本人授权下保存真实原声，用户知道是否保存成功，中断后可恢复已保存素材。
3. 生成可核对故事，编辑与本人确认对应确定版本。
4. 双方确认的 PDF 就是交给印厂的文件，交接与物流可追踪。
5. 发生失败、撤回、导出、删除、退款或质量问题时，有明确入口、处理人和可信结果。

每项设计用同一问题检验：删掉它，会使上述结果失败，还是只会减少未来变体的便利？前者保留；后者优先固定规则或受控人工处理。自动化是否值得建设，应由实测频率、人工耗时和错误成本决定。

## 不能用“首批量小”省略的部分

- 付款、退款与首本唯一性：两次点击或回调重放就会发生，不需要高并发才有风险。
- 登录账号、讲述者与操作人分离：否则同机协助会被误记为本人登录或本人确认。
- 原声封存、私有访问和可恢复任务：一次丢失或泄露就破坏用户的购买理由。
- 确认版本、PDF hash 与交接记录：纸书不可原地修复，错版代价高。
- 撤回生效、迟到结果拒绝和删除恢复台账：小样本同样可能在重试、备份恢复时重新产生已删除资料。
- 真机、真实供应商与实物验收：自动测试无法证明收音、口音理解和印刷体验。

这些机制可以集中在少数模块内，通过简单 Interface 使用；无需让每个调用方理解锁、队列与供应商恢复细节。

## 建议的执行优先级

1. 先由产品/运营冻结首版实际政策，让工程只实现已选规则；不再由枚举倒逼业务增加方案。
2. 每张生产票开始前明确复用哪些探针能力、补齐哪些生产约束，避免第二套实现。
3. 为运营票明确“人工判断 + 受控执行”的可验收结果，不将所有人工步骤自动产品化。
4. 继续收敛规范正文与测试入口，维持 30 张票结构，并尽早用同一份内部样本贯通素材、故事、PDF 和纸书链路。

已有模块不因本次审视被推倒重写。已确认的同机协助、个人计划编辑、可选追问、照片和资料权利仍属于 MVP；删除它们属于产品范围变化，需要单独决定，不能包装成纯工程简化。
