## 实现结果

本人、客服撤回及换绑在用途/epoch 事务中记录不可改写的最少联动事件，提交后才清理任务/暂停生产；后续执行失败不恢复访问。未执行记录可由进程补扫与状态查询恢复。T12 当次协助用途保持独立，以本用途的新拒绝 Session fence 生效，不为拒绝 AI 而撤销其他协助用途。

私有原声/Range、固定书中原声、照片及特定资产、用户书稿 PDF、运营生产 PDF 通过同一活动流机制逐块重验，并在提交撤回后终止旧活动流。已经接收的设备字节不能回收。当前账号和权限每块检查，跨 API 进程/背压空闲流由 PostgreSQL 轮询补验。

旧任务失效并增加 fence；仅未进入外部传输的 `preparing` 费用预留可以释放，传输未知保留核实依据。交接前停止，交接后取消待人工核实；已交付实物保留事实。不释放或新增首本权益，不清除 Commerce 的独立冻结。换绑保留 subject 与历史确认。

本人/同机页查询最少撤回处置，不依赖已撤销的内容访问；客服共享工单可代录指定用途并核验，展示实际生产状态、处理人和期限。私人页面定期查询当前权限，撤回/换绑后清理显示、草稿和临时回听/预览；采访页按原采集核验入口停止继续录音，本机原文件保留。完整复现见[撤回与活动访问](../../../development-withdrawal.md)。

## 独立审查与 CI 修复

候选 `9e86640` 的独立 Spec/Standards 分别指出两项 P2，PR CI 40331934719 同时发现一项源码导入失败。原候选不作合并依据，三项均沿公开行为复现修复：

1. **同 epoch 协助恢复误伤新授权。** 新增真实 PG/Redis + HTTP 测试：拒绝后的联动故障 → 同 epoch 重新协助授权 → 新录音/排队任务及真实活动流 → 旧事件补扫。原版把新任务变成 invalidated（RED `/tmp/timenook-t24-red-assisted-recovery.log`）。现在拒绝事务捕获精确旧 task id/fence、旧 Session 及当时生产尝试，恢复只对所捕获 fence 做 CAS；活动流固定单调撤回序号，关闭只作用于相应序号之前的相关流。新旧任务/事件强制使用完全相同的数据库 createdAt，仍能保留新任务 queued、新流完整结束，并使旧任务失效。先前迁移保持不变，追加 `20261026121000_revocation_targets`；旧候选缺少精确目标的未执行遗留项保持待人工，不能自动重新圈入后来的工作。
2. **同机照片被共享权限误挡。** 新 Page 测试真实 RED：原版持续停留时错误请求 participation。改用原 collection-check + 当次 assistedSessionId；只授权采集而未授权共享仍可停留/上传，实际拒绝后才清理。RED `/tmp/timenook-t24-red-assisted-photos.log`；相关照片与原始项目媒体公开用例 22/22 GREEN。实际浏览器也断言 canRead=false，通过当次采集许可完成上传，再拒绝采集自动清理。
3. **Node TSX 直接源码导入。** 本机 Node22/TSX 复现与 Linux CI 相同的 `CONSENT_PURPOSES` named export 错误（`/tmp/timenook-t24-red-direct-import.log`）。公共只读 watcher 改为仅依赖 sessionClient 和 type-only 合约，照片 watcher 使用独立的原采集边界；原 `tests/project-media.test.ts` 直接导入真实 story 页恢复 GREEN，不改测试为跳过或把故障归给环境。原生 bundler/编译与新 PR CI 分别验证设备构建及 Linux。
